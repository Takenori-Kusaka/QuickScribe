# パフォーマンス・ベースライン

> Status: Living（2026-06-29 初版）。計測方法と基準値を記録する（#403）。実測は `perf-bench` ワークフローのアーティファクト（`perf-report.md`）が一次情報。

## 計測方法

- **ワークフロー**: `.github/workflows/perf.yml`（`workflow_dispatch` ＋ release 公開時）。
- **対象**: ローカル whisper（`ggml-tiny`、Linux x64、決定的 AVX2 ベースライン / [ADR-0012](../adr/0012-windows-multiarch-multisimd-distribution.md)）。
- **指標**:
  - **RTF（実時間比）** = 文字起こし経過秒 / 音源長秒。**< 1.0 が実時間以内**の目安。
  - **ピークメモリ（RSS）** = `/usr/bin/time -v` の Maximum resident set size。
- 固定音源（espeak-ng の既知発話・約十数秒）で計測。コンパイルは事前ビルド（`--no-run`）で計測区間から除外。

## 目標（暫定 / [NFR](../non-functional-requirements.md)）

| 指標 | 目標（暫定） |
|---|---|
| RTF（tiny / x64 AVX2） | ≤ 1.0（実時間以内） |
| ピークメモリ（文字起こし時） | ≤ 300 MB 目安 |

## ベースライン実測

| 日付 | バージョン | モデル | 音源長 | RTF | ピークRSS | 備考 |
|---|---|---|---|---|---|---|
| 2026-06-29 | v0.6.4時点 | ggml-tiny | 18.88s | **0.857** ✅ | 1518.9 MB※ | GitHub Actions ubuntu-22.04 x64・AVX2。RTF<1.0=実時間以内（目標達成） |

> ※ ピークRSSは **`cargo test` ハーネス全体**の値（テストプロセス＋ビルド成果物＋whisperコンテキスト）であり、**配布アプリのアイドル時メモリではない**。アプリ実体のメモリ計測（GUI起動時）は #403 後続で別途行う。RTF は実用域（実時間以内）を確認。

## 起動時間・アイドルメモリ（#554 / #403）

- `perf.yml` の `startup-time` ジョブが xvfb ヘッドレスで `run()` 入口→フロント `onMount` の経過をアプリ計装で記録（`QS_PERF_STARTUP=1`）。
- 同ジョブで ready 後に**アプリ実プロセス(quickscribe)のアイドル RSS** をサンプルしピーク値を記録（`cargo test` ハーネス値ではなく配布バイナリ実体）。値は `startup-report.md` アーティファクト＋ジョブサマリが一次情報。

## アイドル CPU 使用率（#664 Phase 1）

常駐アプリで最も効く資源指標だが、従来 NFR にも perf CI にも存在しなかった（アイドル RSS のみ計測していた）。

### 計測方法（Linux / `perf.yml` の `startup-time` ジョブ）

- ready（`perf-startup.txt` 生成）を確認したのち **3 秒待つ**。
- そこから **10 秒 × 6 区間（合計 60 秒）**の観測窓を取り、**区間ごとに**対象プロセス群の `/proc/<pid>/stat` の **`utime + stime`（tick）** をサンプルして Δtick と使用率を出す。
- 対象は **`quickscribe`（アプリ実体）と `WebKit(WebProcess|NetworkProcess)`（WebView の子プロセス）** の合計。RSS 指標がアプリ実体のみなのに対し、CPU は WebView 側の常駐コストを取りこぼすと意味を成さないため対象を広げている。
- 使用率(%) = `(Δtick / CLK_TCK) / 経過実時間秒 × 100`。**1 コア基準**（100 % = 1 コア占有）。
- 出力先は `startup-report.md` アーティファクト＋ジョブサマリ（起動時間・アイドル RSS と同じ扱い）。区間別内訳の表も同時に出る。
- アイドル RSS はこの 60 秒を通してサンプルする（60 サンプルのピーク）。

**判定に使うのは「定常」＝第 2〜6 区間（50 秒窓）。** 第 1 区間は**旧定義（settle 3 秒 + 10 秒窓の 1 点測り）そのまま**で、過去の実測と比較するための参考値として残している。

#### なぜ区間分割にしたか（#678）

当初は **10 秒窓の 1 点測り**だった。同一コミット `c5f2109` で 3 回測ると **8.78 / 4.05 / 5.72 %（2.2 倍の開き）**で、回帰ゲートの閾値を置けなかった。

そこで「settle が短く起動処理の残りを窓が掴んでいる」のか「xvfb の WebKitGTK が定常的に焼いている」のかを **1 ランで区別できる形**（区間別に出す。前者なら第 1 区間だけ高く、後者なら全区間が横ばい）に変えた。

**結果は前者だった。** 第 1 区間 6.65〜20.12 % に対し第 2 区間以降は 0.00〜0.39 %（下表 N=5）。**xvfb の定常コスト説は否定された** — 定常的に焼いているなら全区間が横ばいに高いままになる。旧 3 本（8.78 / 4.05 / 5.72 %）は新定義の第 1 区間の分布にすべて収まるので、**過去のバラつきの正体は「起動処理の残りをどれだけ掴んだかの当たり外れ」**だったことまで説明が付く。

> 切り分けの途中で使った**誤った根拠**を記録しておく。当時は「同じ観測窓で採った RSS が 150.3 / 150.6 / 150.7 MB と 0.3 % 以内で一致しているのだから、ランナー全体の遅速ではなく CPU 側固有の問題だ」と論じた。**結論は正しかったが根拠は誤り**で、N=5 まで取ると RSS も **150.9〜230.4 MB（1.5 倍）**振れる。3 本が偶然同じ水準だっただけである。**「安定して見える指標」を N=3 で論拠にしてはいけない。** 仮説が決着したのは区間別内訳という直接の観測によるもので、RSS の一致とは関係がない。

> 教訓: **観測窓は「対象環境の起動時間」に対して置く。** このランナーの起動は約 31 秒で、settle 3 秒はその 9.5 % にすぎなかった。Windows 実機は起動 1〜2 秒程度なので同じ 3 秒が 150〜300 % に相当し、そちらでは問題にならなかった。**同じ定数が環境によって「十分」にも「まったく足りない」にもなる。**

### この計測でカバーできない範囲（重要）

perf CI は **ubuntu-22.04 / xvfb** で走る。一方タスクバーウィジェット（#662）は **Windows 限定コード**（`src-tauri/src/taskbar_widget.rs`）であり、**Linux CI には原理的に現れない**。**Linux の数値だけを見て「アイドル CPU は問題ない」と判断してはならない。** Windows 側は次節の手順で計測する。

二峰性は「起動時に通る経路が 2 通りある」ことを示唆する（推測）。CPU 側が決着したのとは**別の問題**なので、#678 に残して切り分けを続ける。

#### RSS の一次指標は「定常ピーク」（PO 決定）

現行の `startup-report.md` は**全窓ピークと定常ピーク（第 2 区間以降）を両方出す**。このうち**一次指標は定常ピーク**とする。

- **理由**: NFR の `≤ 300 MB` は**常駐アプリのアイドル時フットプリント**についての目標である。起動処理中の一過性ピークを同じ行で判定すれば、**CPU で起きたのと同じ誤り（起動処理の残りを掴む）を RSS で繰り返す**ことになる。
- **全窓ピークは捨てない。** 「**起動時ピーク RSS**」という別の観測量として併記し、二峰性（#678）調査の一次データとして使う。定義は変えていないので過去の記録との比較も切れない。
- **達成判定は保留。** 定常ピークにも二峰性が出るなら「達成 ✅」は付けない（#678 の原因特定が先）。目標 ≤300 MB は両方の峰が満たすのでリリースは止めない。
- **RSS の回帰ゲートは今回置かない。** 原因未解明の 1.5 倍振れの上にゲートを置けば偽陽性になる。#678 の解決後に置く（指標の取り下げではなく段階実装）。

ADR-0033（[#675](https://github.com/Takenori-Kusaka/QuickScribe/pull/675)）が決めるのは**計測対象プロセス集合**（アプリ実体のみ → 実体＋WebView 子プロセス群）、ここで決めたのは**観測窓**であり、二軸は直交する。RSS 指標 =（プロセス集合: 実体＋WebView2）×（観測窓: 定常）として両方同時に確定できる。

> 定常ピークの実測は run 6（[30222252075](https://github.com/Takenori-Kusaka/QuickScribe/actions/runs/30222252075)）の **146.5 MB**（同ランの全窓ピークは 151.1 MB）の**1 本のみ**。この run は低い峰に落ちているので、**高い峰（~223–230 MB）のときに定常ピークがどうなるかはまだ分かっていない。** 二峰性の原因が起動処理の残りなら定常ピークは低い峰に寄るはずで、そうならなければ別の要因が残っている、という切り分けに使える。

### 回帰ゲートの閾値（#664 Phase 3）— 決定

**定常 CPU ≤ 0.50 %。** 値は **`docs/perf/idle-cpu-baseline.json`** に置き、workflow にハードコードしない（`ja-cer-baseline.json` と同じ運用。更新は PR で明示する）。

#### 上限は実測から導出しない（構造の決定・PO）

**`limit_pct` は独立した運用値であり、`observations` から計算しない。** JSON は次の 3 つを分けて持つ。

| キー | 役割 |
|---|---|
| `limit_pct: 0.50` | **運用値。** ゲートが比較する唯一の数字 |
| `early_warning_pct: 0.25` | **早期警戒線**（上限の 1/2）。超えたらゲートを緩めず原因を調べる |
| `early_warning_escalation` | 警戒線超過が**調査に上がる条件**（持続性）。単発は記録のみ |
| `observations` | **観測記録**（N / min / max / median / samples）。基準ではない |

**サンプルを足したときに更新するのは `observations` だけで、`limit_pct` は動かない。** `limit_pct` を変えてよいのは「観測窓の定義を変えた」「計測対象プロセス集合を変えた（ADR-0033）」「分布が安定したので**より厳しく**引き締める」の 3 つで、**「実測 max が上がった」は理由にならない**。実測が上限へ近づくのは**ゲートが仕事をしている状態**であって、緩める根拠ではない。

> **この構造にした経緯。** 0.50 % は決定時に「N=6 の実測 max 0.16 % ＋ 絶対マージン 0.34 pt」として導出した。その直後に 7 本目が **0.20 %** を出して実測 max が動き（上表 run 7）、「上限を 0.54 % へ付け替えるべきか」という問いが発生した。答えは「据え置く」で正しかったが、**同じ問いが N=9 でまた出る構造**になっていた。上限を実測から独立させたのは、次の人がこの判断をしなくて済むようにするためである。「baseline + margin」は 0.50 を導いたときの説明であって、運用値の定義ではない。

**早期警戒線 0.25 %（= 13 tick / 50 秒）。** 1 tick = 10 ms の分解能ノイズでは説明が付かない水準で、**「何かが常駐し始めた」可能性が実在する**。ここで上限を 0.60 % に上げるのはゲートを捨てるのと同じである。**現在の実測 max は 0.20 % で、既に警戒線に近い。** `perf.yml` は上限超過（回帰）と警戒線超過を別の警告として出し分ける。

#### 警戒線は動かさない。動かすのは「調査に入る条件」のほう（**QS-Dev 提案・PO 判断待ち**）

> **この節は PO 決定ではない。** 警戒線 0.25 % と「超えたらゲートを緩めず原因を調べる」までが PO 決定で、**以下の持続性条件（単発は記録のみ / 連続 2 本 or 直近 10 本中 3 本で調査）は QS-Dev の提案**である。実装は入れてあるが、**採否の判断は PO に委ねる**。却下される場合は `early_warning_escalation` を外し、単発で調査に入る形へ戻せばよい（`perf.yml` 側は分岐 1 つの削除で済む）。

実測 max 0.20 % に対し警戒線 0.25 % までの余裕は **1 tick（0.02 pt）× 2.5** しかない。実測は 50 秒あたり 4 / 5 / 6 / 7 / 7 / 7 / 8 / 8 / 10 / 10 tick で、**tick はカウントデータであるから、この散らばりなら 11〜13 tick が何も変わらずに出ること自体は起こり得る**（分布の形までは N=10 では主張できない）。

**それでも警戒線 0.25 % は動かさない。** 実測が上端に寄ったことを理由に警戒線を上げるのは、`limit_pct` について「実測が動いたことは変更理由にならない」と決めたのと**同じ誤り**である。警戒線はゲートではないが、**同じ力学に晒されている。**

代わりに**発火条件に持続性を足す**（`early_warning_escalation`）。

| 条件 | 動作 |
|---|---|
| 1 本だけ 0.25 % 超 | **記録のみ。** 警告は出すが調査には入らない |
| **連続 2 本** 0.25 % 超 | **調査に入る** |
| **直近 10 本中 3 本** 0.25 % 超 | **調査に入る** |

**2 つ目の条件が必要な理由**: #678 の RSS 二峰性のような**間欠的な事象は連続しない**。連続だけを条件にすると、**2 回に 1 回だけ跳ねる回帰を永久に拾えない。**

これで「線が低すぎて毎回鳴る」も「線を上げて意味を失う」も避けられる。**変えたのは調査の起動条件であって、0.25 % という水準の意味は変えていない。** 単発が鳴ることを理由に警戒線を上げてはならない。

**判定に使う時系列は `observations.samples`（時系列順）＋今回の実測値。** `samples` を並べ替えると「連続 2 本」の判定が壊れる。

> **制約（未解決）**: `samples` は現状 **PR で人が追記する**。したがって「連続 2 本」は追記されるまで成立しない。**CI 側で時系列を自動収集する形**（過去ランの `startup-report` アーティファクトから系列を組む）は、#664 Phase 3 の**段 1（`push: main` での実行）を入れる PR**で扱う。段 1 が入るまで、この持続性判定は人の追記に依存する。

**ベースライン比（相対ゲート）は採らない。** 定常の Δtick は 50 秒で 4〜10。**1 tick = 10 ms の分解能の底に張り付いている。** この水準で相対ゲートを置くと、4 tick → 8 tick が「+100 % 悪化」として発火するが実際は 0.08 % → 0.16 % であり、**常駐アプリとして何も悪化していない。** 偽陽性で CI が赤くなり続け、指標そのものが無視されるようになる。

**NFR と同値の 1.0 % も採らない。** NFR は「**ユーザー端末で許容できる上限**」、回帰ゲートは「**今より悪化していないか**」で目的が違う。同じ数字を置くと回帰ゲートが NFR チェックの重複になり、回帰検出の機能が消える。

0.50 % の妥当性:

- 分解能ノイズ（±1 tick = ±0.02 pt）の **25 倍上**。偽陽性は踏まない
- 実測最大 0.20 %（N=10）の **2.5 倍**の余裕、NFR（1.0 %）の **1/2**
- **常駐処理が入り込めば確実に捕まる。** 例: 300 ms ポーリングが 1 回あたり 3 ms 消費すれば 25 tick/50 秒 = 0.5 pt。現在の水準 0.20 % に上乗せされて 0.70 % となり上限を超える

RTF / CER が相対ゲートなのは、それらが**モデルとハードの性能比**という連続量で、絶対値に意味が無いため。アイドル CPU は**「余計な処理が動いているか否か」**の指標で、性質が違う。同じ方式を機械的に当てはめる理由は無い。

**運用上の制約**:

- **観測窓の定義を変えたら閾値を再校正する。** 定常窓は「ready + 3 秒 settle の後、10 秒 × 6 区間のうち第 2〜6 区間（50 秒）」で固定する。窓を変えれば値の意味が変わるため、閾値をそのまま持ち越してはならない。
- **再校正トリガー: 起動時間が 40 秒を超えたら、窓定義と閾値を必ず再校正する。** 現在の定常窓の開始位置は「ready + 3 秒 + 10 秒」という**固定値**であり、この節が記録した誤り（settle 3 秒が起動 31 秒の環境には足りなかった）を窓の定義自体はまだ体現していない。**ランナーの変更や機能追加で起動が 60 秒になれば第 1〜2 区間が起動処理で汚染され、閾値 0.50 % は静かに偽陽性を出し始める。** 実測の起動時間は 30.8〜32.6 秒（CI N=10）なので、40 秒は「まだ余裕がある / もう危ない」を分ける観測可能な境界として置いている。**ゲートが赤くなったら、まず起動時間を見ること。**
- 動的な定常検出（連続 2 区間の Δtick が閾値以下になった時点を定常の開始とみなし、固定値をやめる）は **#664 Phase 3 以降の課題**として残す。上の 40 秒トリガーはそれが入るまでの最小の防御である。
- #678 の二峰性が解け、N が積み上がって分布が安定したら **0.30 %（15 tick 相当）への引き締めを検討**する。緩い方に置いて放置しない。

#### ゲートの実行契機 — 段階導入と、順序を入れ替えてはいけない理由

`perf.yml` の `on:` は `workflow_dispatch` と `release: published` だけなので、**このままではゲートとして成立しない**（回帰が入った PR は止まらず、リリース公開後に初めて赤くなる）。PO 決定は 3 段階での導入。

| 段 | 契機 | 判定 |
|---|---|---|
| 1 | `push: branches: [main]` | **赤くする**（`exit 1`。`n/a`＝計測不能も赤にする。計測できないゲートは無いのと同じ） |
| 2 | `pull_request`（paths filter 付き・required にしない） | 赤くするが merge はブロックしない。偽陽性の実績を溜める期間 |
| 3 | 段 2 で 10 本以上連続して偽陽性ゼロ → required に昇格 | ブロックする |

**段 1 を飛ばして段 2 から始めてはならない。CI 時間の問題である。**

このジョブの rust-cache キーは **`v0-rust-startup-time-Linux-x64-<hash>`**（実測: [run 30204338284](https://github.com/Takenori-Kusaka/QuickScribe/actions/runs/30204338284) のログ）。Swatinem/rust-cache はキーにジョブ名を含めるため、**`ci.yml` の `build` ジョブが温めたキャッシュはこのジョブには効かない。** そして GitHub Actions のキャッシュは **PR ブランチのものが他 PR から見えず、PR からは既定ブランチ（main）のキャッシュだけが復元できる**。

→ **段 1（`push: main`）で main 側のキーを温めていない状態で段 2 を置くと、PR は毎回 cold ビルドを払う。** 実測は cold **7 分 22 秒**（`No cache found.` をログで確認・旧 10 秒窓のため現行 60 秒窓では約 8 分 10 秒）に対し warm **5 分 27 秒**。段 1 が段 2 の前提条件である。

**実装上の注意**（PO 決定）:

- **`perf.yml` 全体に `pull_request` を付けない。** 同ファイルに `ja-accuracy` / `ja-cer-corpus`（large-v3-turbo を DL する重量ジョブ）が同居している。`startup-time` を別ワークフローへ切り出して `workflow_call` 化し、`perf.yml` から呼ぶ（#427 で `release.yml` に採ったのと同じ手法）
- paths filter: `src-tauri/**` / `src/**` / `package.json` / `package-lock.json` / `src-tauri/Cargo.{toml,lock}` / 当該ワークフロー自身
- 段 3 で required にすると **paths filter で skip された PR が pending のまま固まる**（GitHub の既知挙動）。`if: always()` の集約ジョブで success を返す形での回避を段 3 の受入基準に含める

## アイドル CPU 使用率 — Windows 実機（#664 Phase 2）

### 計測手順

`scripts/perf/measure_idle_cpu.ps1` を使う。Linux ジョブと**同じ定義**（消費CPU秒 / 経過実時間、1コア基準）で算出する。

```powershell
# 0. 診断ログを有効にしてから起動する（タイマーが実際に回っていることの確認手段）
#    #667 以降 taskbar-diag.log は既定 OFF。これを立てないと show/hide 遷移を観測できない。
$env:QS_TASKBAR_DIAG = "1"

# 1. QuickScribe を起動し、操作せず放置する（＝アイドル状態にする）
# 2. 観測窓 120 秒で計測する
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/perf/measure_idle_cpu.ps1 -Label widget-on -WindowSeconds 120 `
  -JsonPath idle-cpu-widget-on.json

# 3. 設定でタスクバーウィジェットを OFF にし、同じ長さで計測して差分を取る
powershell -NoProfile -ExecutionPolicy Bypass `
  -File scripts/perf/measure_idle_cpu.ps1 -Label widget-off -WindowSeconds 120 `
  -JsonPath idle-cpu-widget-off.json
```

- **`QS_TASKBAR_DIAG=1` を立てずに計測してはならない。** ウィジェットのタイマーが回っていることの唯一の確認手段が `taskbar-diag.log` の `show`/`hide` 遷移であり、#667 でこのログは既定 OFF になった（[troubleshooting.md](../guide/troubleshooting.md)）。立て忘れると「タイマーが動いているつもりで動いていない」数値を掴む。
- 計測対象は `quickscribe.exe` **とその子孫の `msedgewebview2.exe` 群**（WebView2）。`per_process` にプロセス別内訳が出るので、**タイマーが回るアプリ実体単独の消費**を WebView2 と切り離して読める。
- ウィジェット ON/OFF の差分が意味を持つのは、設定 OFF 時に `WM_TIMER` ハンドラが `ENABLED` の atomic 読みだけで早期 return するため（`taskbar_widget.rs:475-483`）。**高価な Win32 呼び出し群（`GetForegroundWindow` / `FindWindowW` / `SHAppBarMessage` / `SetWindowPos`）は OFF 時には走らない**＝差分がウィジェットの寄与になる。
- **CI 化はしていない。** `windows-latest` ランナーで `Shell_TrayWnd`（explorer のタスクバー）が成立する保証がなく、成立しなければウィジェットは配置されず寄与がゼロになって計測の意味が消える。ヘッドレス Windows での成立可否が確認できるまでは、本手順による**実機での手動計測**を一次情報とする。

### 実測（Windows 実機）

| 日付 | ビルド | 観測窓 | アイドル CPU 合計 (1コア基準) | アプリ実体単独 | WebView2 合計 |
|---|---|---|---|---|---|
| 2026-07-26 | main 相当のローカル release ビルド | 30 s | 0.052 % | — | — |
| 2026-07-26 | 同上 | 120 s | **0.117 %** | **0.091 %** | 0.026 % |

計測環境: Windows 11 Pro 26200 / ウィジェット有効（`taskbar-diag.log` に `show`/`hide` 遷移あり＝300ms タイマー稼働中）/ プロセス7件（実体1 + WebView2 6）。

**目標 ≤ 1 % に対して 1桁小さい。** タスクバーウィジェットのタイマーが動いている状態でこの値なので、**#662（300ms ポーリングのイベント駆動化）の CPU 面での上限効果は 0.09 %/1コア 未満**である。静的なコード読解では「毎秒3.3回の Win32 呼び出し」に見えたが、実測では 1 tick あたり 1 ms 未満だった。

> 注: `TotalProcessorTime` の分解能は約 15.6 ms のため、120 秒窓での 0.109 秒は約 7 量子分。絶対値の精度は粗いが、**「1 % を大きく下回る」という桁の判断には十分**。
