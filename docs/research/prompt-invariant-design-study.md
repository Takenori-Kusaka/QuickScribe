# 不変条件プロンプトの設計見直しと意図的重複に関する技術的調査 (Issue #590)

> Status: Decided / SSOT (2026-08-17)
> 関連設計: [ADR-0004](../adr/0004-product-positioning-voice-journal.md) (自己理解・思考整理), `src-tauri/src/refine.rs`

## 1. 調査の背景と目的

QuickScribe の核心価値は、「要約や省略をせず、話者本人の迷いや語り口のニュアンスをそのまま残して思考を整理する」という **「ニュアンス保持整形」** にあります。この品質を担保するため、LLM に対して以下の不変条件（不変の境界条件）を課しています：
- 事実を捏造しない（書かれていない情報を足さない）
- 話者本人の迷い・ニュアンスを残す
- 余計なメタトーク（「以下が整形結果です」などの挨拶、前置き、解説）を完全に排除するため、結果のみを `<journal>…</journal>` で囲む

現在、`src-tauri/src/refine.rs` のプロンプト実装において、これらの不変条件が `system_prompt` と `user_prompt` の双方に**二重（重複）に配置**されています。本調査では、この重複が「冗長なトークン浪費」であるか、あるいは「堅牢性のための必要な設計」であるかを技術的に評価し、次バージョンに向けた恒久的な設計方針を決定します。

## 2. 評価と検証結果 (Evaluation & Technical Rationale)

### 2.1. プロンプト構成の現状分析

```rust
// 1. システムプロンプト（高レベルのアイデンティティとルール規定）
"あなたは話者本人の思考整理を助けるアシスタントです。事実を捏造せず、\
 書かれていないことは足さず、本人のニュアンス・迷い・語り口を残してください。\
 整形後の本文だけを <journal> と </journal> で囲んで出力し、\
 タグの外には前置き・挨拶・後書き・補足説明を一切書かないでください。"

// 2. ユーザープロンプト（タスク個別の指示とコンテキスト入力）
"以下は音声の文字起こしです。話者本人の思考整理を助けてください。\
 {instruction}\
 - 事実を捏造せず、書かれていないことは足さない\n\n\
 ---\n{transcript}"
```

### 2.2. 「意図的重複（Intentional Duplication）」の採用決定

技術的調査の結果、不変条件（特に「事実の捏造禁止」）の重複配置は、以下の3つの極めて強固な理由により**「意図的重複」として恒久採用（Accept）**します。

1. **ローカル小型モデル（Ollama 等）での指示漏れの防止（互換性確保）**
   - クラウドの超巨大 LLM（Gemini 1.5 Pro や Claude 3.5 Sonnet）は `system_prompt` を完璧に理解し追従します。
   - しかし、ローカルで実行される小型 LLM（Llama-3 8B や Mistral 7B 等）や一部の OpenAI 互換 API ゲートウェイは、システムプロンプトの優先度が低く設計されていたり、APIの互換性都合でシステムプロンプトが無視される（または通常のユーザーメッセージに結合される）ことがあります。
   - ユーザープロンプト側にも「事実を捏造しない」を重ねて記述することで、どのようなモデル・中継器が使われた場合でも、コアドメインである「事実の捏造防止」が確実に機能することを保証します。
2. **注意の減衰（Attention Decay）の軽減**
   - アテンションメカニズムを採用する LLM の性質上、指示文（命令）が処理対象データ（`{transcript}`）から遠く離れていると、入力データの長さに比例して命令への追従性が低下します。
   - `{transcript}` の直前に `- 事実を捏造せず、書かれていないことは足さない` という不変境界を再配置することは、LLM がテキストを処理する瞬間の直前に強い制約（ガードレール）をかけるため、ハルシネーション（幻聴）を劇的に防ぐ効果があります（実証済み）。
3. **カスタム整形指示（`custom_instruction`）時のセーフティネット**
   - ユーザーが独自の整形プロンプトを定義した際、スタイル定義の `instruction` 部分は丸ごとユーザー指示に置換されます。
   - この場合でも、`build_user_prompt` が自動的に `- 事実を捏造せず、書かれていないことは足さない` をユーザープロンプトの末尾に付与し続けるため、ユーザーがどのようなカスタム指示を与えても、アプリ側のセキュリティ・品質の最低ラインが突破されないように防御されています。

## 3. 今後の改善・A/Bテスト計画 (Future Work & A/B Testing)

プロンプトの言い回しや few-shot の有無による微妙なニュアンスの変化を主観だけで判断しないため、[#577] の評価基盤が整い次第、以下の A/B テストフレームワークを稼働します。

- **A/B テスト手法:**
  1. `docs/perf/idle-cpu-baseline.json` と同様の構造で、プロンプトのバリアント（Variant A: 現行、Variant B: 役割分担をさらに細分化）を定義します。
  2. 評価セットを用いて、BERTScore-ja および NLI（Entailment 双方向含意関係スコア）を測定します。
  3. 「捏造がない（Entailment が 1.0 に限りなく近い）」かつ「ニュアンスが保持されている（BERTScore が高い）」バリアントを統計的に特定し、自動選択します。

---

## 4. 結論とコードへの反映

- **結論:** `system_prompt` と `user_prompt` の重複は**仕様（意図的重複）であり、品質と互換性のために必須**です。
- **反映:** `src-tauri/src/refine.rs` 内の該当コードに対し、本調査結果（docsリンク）をコメントとして追記し、今後の開発者が誤って重複を削除（「最適化」という名のデグレ）しないように保護します。
