# ADR-0033: トレイ常駐時に WebView2 を破棄せず保持する（常駐メモリ約 195 MB の受容）

- Status: Proposed（Deciders 承認待ち）
- Date: 2026-07-26
- Deciders: Takenori Kusaka
- 関連原則: CLAUDE.md 差別化軸「物理ボタン統合体験」（押した瞬間に録れる即時性）／[ADR-0006 スコープ完全性](0006-scope-completeness-policy.md)（本ADRは機能の削減ではなく、**既に実装されている挙動の明文化**）
- 関連: [ADR-0014 物理トリガー連携](0014-physical-trigger-integration.md)（即時性がこの決定の主根拠）／[ADR-0005 技術スタック](0005-tech-stack.md)（Tauri/WebView2 採用）／[非機能要件](../non-functional-requirements.md) 1章 アイドル時メモリ（RSS）／[perf/baseline.md](../perf/baseline.md)（実測内訳）

## 背景・課題

常駐リソース最適化の調査（#662〜#667）の過程で、Windows 実機のアイドル時メモリ内訳が初めて実測された（2026-07-26・[perf/baseline.md](../perf/baseline.md) 「参考: アイドル時メモリ」節）。

| プロセス | RSS |
|---|---|
| `quickscribe.exe`（アプリ実体） | 29.8 MB |
| `msedgewebview2.exe` × 6（WebView2） | 165.5 MB |
| **合計** | **195.3 MB** |

**常駐メモリの約 85 % は WebView2 側**である。つまり Rust 側のメモリを削っても常駐メモリの実態はほとんど動かない。#663（原音バッファをRAMに抱えない）のような Rust 側の削減は、それ自体は正しい改善だが、常駐フットプリント全体に対しては桁が違う。

この内訳が意味するのは「**常駐メモリを本気で下げるなら、トレイ常駐時に WebView2 を落とすしかない**」ということである。実装上は `lib.rs` の `CloseRequested` ハンドラが `api.prevent_close()` + `window.hide()` を行っており、ウィンドウは破棄されず WebView2 プロセス群も生き続ける（`--minimized` 起動時も同様に hide で開始する）。

この「破棄せず保持する」という判断は**既にコードに埋まっているが、ADR として明文化されていない**。根拠が残っていないため、リソース最適化の文脈で「WebView2 を落とせば 165 MB 減る」という提案が繰り返し浮上しうる。

## 決定

**トレイ常駐（ウィンドウを閉じた状態）でも WebView2 を破棄せず保持する。合計 195 MB 程度の常駐メモリを受容する。**

根拠:

1. **即時性は差別化軸そのもの**。QuickScribe の中核体験は「物理ボタンを押した瞬間に録れる」ことである（CLAUDE.md 差別化軸「物理ボタン統合体験」・[ADR-0014](0014-physical-trigger-integration.md)）。ウィンドウを破棄すると、復帰時に WebView2 プロセス起動＋フロントエンドの再初期化が必要になり、この即時性を直接損なう。**削ってよいのはコモディティ側のコストであって、差別化軸ではない。**
2. **NFR 目標を満たしている**。アイドル時メモリの目標は 300 MB 目安で、実測 195.3 MB は目標内。緊急性はない。
3. **常駐アプリとしての妥当性**。ブラウザエンジンを内包する常駐アプリとして 195 MB は逸脱した値ではない。

### 却下案

- **(a) hide 時に WebView2 を破棄し、表示時に再生成する** — 165 MB を回収できるが、復帰レイテンシが即時性を損なう。加えて録音状態・ジョブ一覧といった UI 状態の復元が必要になり、状態同期のバグ面を増やす。**回収するリソースの大きさより、失う体験の方が高い。**
- **(b) 録音経路のみ Rust 側に寄せ、UI は破棄する** — 録音自体は既に Rust 側で完結しており技術的には成立しうるが、録音開始のフィードバック（オーバーレイ・タスクバーウィジェットの状態）まで含めた体験の一貫性が崩れる。ウィジェット（`taskbar_widget`）は Win32 側なので生き残るが、hide 中と表示中で挙動が変わる面が増える。

## 結果・トレードオフ

- **Pro**: 復帰の即時性を維持。UI 状態の復元ロジックを持たない（バグ面を増やさない）。実装は現状のままで追加コストゼロ。
- **Con/リスク**: 常駐メモリが 195 MB で固定される。低メモリ環境（4 GB 機など）では相対的に重い。将来 NFR 目標を 300 MB より厳しくする場合、この決定が最初に見直し対象になる。
- **副次**: 「Rust 側の常駐メモリ削減」の投資対効果は上限が 30 MB 側にしかないと確定した。以後のリソース最適化は**メモリではなく CPU・電力・描画コスト**を主戦場とすべきである。

## 非機能要件への反映

現行 NFR の「アイドル時メモリ（RSS）≤ 300 MB 目安」は**アプリ実体のみ**を計測対象としていた。実体は 29.8 MB なので、この書き方だと「30 MB / 300 MB で大幅に余裕」と読めてしまい、**常駐実態（195.3 MB）を 10 分の 1 に見誤る**。

→ **計測対象を「アプリ実体 ＋ WebView(2) 子プロセス群の合計」に変更する。** これは #669 で CPU 指標が既に採った定義（「RSS 指標がアプリ実体のみなのに CPU は WebView 側を取りこぼすと意味を成さない」）と揃える方向でもある。目標値 300 MB は据え置く（合計に対してこそ意味を持つ値だったため）。

## 反証・見直し条件（将来の再検討ゲート）

以下が満たされれば**新ADR**で再検討する。

1. **合計 RSS が NFR 目標 300 MB を超える**、または低メモリ環境での実利用で明確な圧迫が報告される。
2. **WebView2 の破棄→再生成が即時性を損なわないと実測で示せる**（復帰から操作可能まで、体感を損なわない時間内に収まる）。この場合は「hide 後 N 分アイドルで破棄する」等の段階案が現実的になる。
3. Tauri / WebView2 側にプロセス休止（サスペンド）機構が提供され、破棄せずにフットプリントを下げられるようになる。
